# RFC-0012: Managing Linux firewalls via libnftnl/libmnl

- Number: RFC-0012
- Title: Managing Linux Firewall via libnftnl/libmnl
- Status: Implemented
- Created: 2026-07-25
- Last updated: 2026-08-09

## Background and Problem

Tinect has directly linked `libnftnl` and `libmnl` in the early days, but subsequent QUICP RST guard
and TUN INPUT exception rules called `nft` executable. This will introduce PATH/version/text syntax
dependencies, fail to ensure that the static deployment environment is available, and also make
error handling and transaction boundaries inconsistent with existing nftnl rules.

## Goals and Non-goals

The goal is to have the Linux firewall control plane construct nf_tables netlink messages entirely
through libnftnl, and send and verify ACKs through libmnl. Non-goals are implementing the nftables
text parser, taking over the host's existing rules, or using the iptables compatibility layer.

## design

### Unify netlink transactions

All Tinect-owned nftables tables, chains, and rules are constructed in `nftnl::Batch`, sent over the
`NETLINK_NETFILTER` socket. `send_linux_nft_batch` must consume the ACK of each sequence in the
batch; any error will cause the operation to fail, and the "command exit code" will not be used as a
success criterion.

### QUICP RST guard

Create an independent `inet` table and `output` base chain for each fake-TCP port. The rule discards
the RST generated by the kernel after matching the following fields; the mark is only excluded when
the carrier mark is explicitly configured:

1. L4 protocol is TCP;
2. If carrier mark is configured, packet mark is not equal to the fake-TCP carrier socket mark;
3. TCP source port is equal to fake-TCP listening port;
4. The RST bit of the TCP flags is set.

TCP flags uses the transport-header original field to read: the 13th byte after the start of the TCP
header (libnftnl's payload original offset parameter is interpreted in bytes), the length is 1, and
then uses bitwise mask `0x04` to match RST. This covers both bare RST and RST|ACK, does not rely on
the `tcp flags` syntax in the `nft` text, and will not accidentally lose the SYN/SYNACK/ACK packets
sent by the fake-TCP raw socket; when explicitly configuring the carrier mark, the RST with this
mark will not be accidentally lost.

### TUN INPUT exception

Each TUN creates independent IPv4 and IPv6 `tinect_input_<tun-name-hex>` tables and `input` base
chains. The suffix of the table name is the ASCII hexadecimal encoding of the actual interface name
to avoid collisions after normalization of different interface names. The chain priority is `-200`,
which is earlier than the host's common INPUT base chain; the rule only matches the target TUN
interface and accepts it. This does not require reading, parsing, or modifying the host-owned
`filter INPUT` chain, nor does it require saving the rule handle. Table names are isolated by
interface, and the clean status carries the exact table name of this instance; if the installation
fails, the pre-existing table with the same name will not be deleted to avoid accidentally deleting
host rules. Egress NAT also uses the `tinect_exit_<tun-name-hex>` table isolated by TUN. Since the
export table is only used by Tinect itself, external rules do not rely on fixed table names;
cleaning is only for the table recorded in this state.

### Errors and rollbacks

The installation process creates tables, chains, and rules in the same batch. If the batch fails,
the caller returns an error but does not use the fixed table name cleanup without state; only the
State object returned successfully is allowed to delete the corresponding table. The created RST
guard will also be cleaned up when QUICP socket initialization fails. Deleting non-existent tables
is a diagnosable error in the cleanup phase, and the caller should handle it according to the
existing life cycle policy.

## Security and Compatibility

The rules only affect the tables and ports named by Tinect itself; RST guard only matches TCP RST on
that port and does not change fake-TCP original packets or normal TCP traffic. The TUN INPUT
exception only allows traffic entering the specified interface and does not change forwarding, NAT,
or host-owned rules. This implementation does not call `nft`, `iptables`, or the shell, does not
rely on PATH, and does not accept external rule text.

## Acceptance and troubleshooting

- No results for `rg 'Command::new\("nft"|run_checked\("nft"' src`.
- `cargo fmt --check`, Strict Clippy, `cargo test` all passed.
- Linux platform test coverage creates and cleans TUN INPUT, exit NAT and QUICP RST guard without
  `nft` executable.
- When `nft -a list ruleset` is used only as an observation tool, you can see the tables, chains,
  priorities and rules consistent with the nftnl structure; it does not depend on this command
  when running.
- When testing QUICP, confirm that `inet tinect_quicp_rst_<port>` exists; when explicitly
  configuring mark, confirm that fake-TCP packets with this mark are not discarded by RST guard;
  when not configured, confirm that RST guard blocks the kernel RST of matching ports.
- When testing TUN input, confirm that the `tinect_input_<tun-name-hex>` chain priority of
  `ip`/`ip6` is `-200`, and there is no legacy table of this Tinect instance after cleaning; the
  candidate table of the same name of another TUN should not be cleaned.

## Implementation Notes

Implements `install_quicp_rst_guard`, `cleanup_quicp_rst_guard`, `install_linux_tun_input_firewall`
and `send_linux_nft_batch` located at `src/platform.rs`. Code that previously manipulated the host
INPUT chain via nft executable has been removed.
