# RFC-0038: Circuit candidate path failure fallback and trunk binding convergence

- Number: RFC-0038
- Status: Implemented
- Created: 2026-08-20
- Last updated: 2026-08-27

> RFC-0046 merges CircuitNoSession and CircuitBroken into a unified CircuitBroken wire feedback
  with `(Link instance, CircuitId)` as the only control association; this RFC's candidate
  quarantine, fallback, and relay abort boundaries still apply.

## Background and Problem

Manually configured circuit paths express priorities in order, but "the first ready candidate" only
means that the topology and capacity proof are established locally, and does not mean that OPEN can
definitely traverse the complete path. The preferred path may fail during the relay forwarding OPEN,
downstream admission, ACK return, or control flow sending stages. Existing reconcilers will only try
the preferred path, so the lower priority direct path will never be used while the preferred path's
Link is still considered ready; this will manifest itself as a circuit with no active path, or a
port with only outbound SYN after DNAT and no return.

In addition, after the relay installs the incoming/outgoing label and binding, if the forwarding
OPEN, OPEN feedback, RENEW or feedback message fails to be sent, some failed branches will only be
logged. Failed labels, leases, and bindings will continue to occupy resources. Subsequent retries or
link replacements may encounter old statuses, forming a black hole or gradually exhausting
resources.

## Goals and Non-goals

Target:

- When there is no active circuit, all ready candidates are tried according to the configured
  priority; when a candidate's OPEN fails to be sent, ACK times out, retry rejection or protocol
  feedback fails to be sent, the next candidate is tried within bounded backoff.
- When a low-priority candidate is established successfully, the migration semantics of the
  preferred candidate are maintained; a brief runtime failure of the preferred candidate must not
  cause an already available active circuit to be incorrectly withdrawn or cause an OPEN storm.
- Candidate failed state only suppresses the same path within the current Link/topology
  generation, is re-evaluated after topology or Link replacement, and all candidates will
  eventually be retried.
- The relay atomically cleans up the binding, bidirectional label and lease on any failed path
  after the binding has been installed; when the downstream OPEN/RENEW/feedback forwarding fails,
  it sends failure feedback signed by this node to the upstream. When the transmission fails, the
  lease timeout serves as an independent backstop.
- Proved through unit testing and privileged multi-node fault injection testing that direct paths,
  multi-hop paths, control message loss, duplicate/late feedback, link replacement and downstream
  restarts can all bounded convergence.

Non-goals:

- Does not change the OPEN, data frame, or end-to-end encryption format and does not allow the
  relay to decrypt the inner payload.
- Do not consider any unreachable path as a ready candidate; candidate fallback does not replace
  topology proof, capacity check, or `EgressPolicy::authorize()`.
- There is no guarantee that the preferred path will be permanently healthy; after the preferred
  path is restored, it will still be migrated according to RFC-0021.

## the term

- **candidate**: The path generated by configuration or pathfinding, and the next hop Link,
  end-to-end topology proof and capacity all pass the check.
- **candidate failure quarantine**: The temporary suppression window after a certain OPEN runtime
  failure; it only affects the current reconciler, not a permanent ACL or topology rejection.
- **relay binding**: The relay is the incoming/outgoing Link binding saved by a Circuit and its
  labels and renewal deadlines on both sides.

## design

### 1. Candidate parsing and runtime rollback

The parser retains all ready candidates in the same order as the configuration order; `preferred` is
still the first item in the list and is used for state and migration. The source worker maintains
the memory table of `(destination, CircuitIdentity)` to backoff status:

1. When there is no active circuit, candidates that have never been in quarantine are tried
   first.
2. OPEN control send failure, OPEN ACK timeout, retryable/non-retryable OPEN rejection, or
   failure of a known path before local submission will put the current candidate into quarantine
   and grow the window with exponential backoff, with an upper limit of a finite constant.
3. The worker immediately tries the next candidate in sequence. The new candidate must establish
   an attempt with its own `CircuitIdentity`, Link instance, capacity vector and generation; the
   generation check of `commit_if_current` cannot be bypassed.
4. If all candidates are in quarantine, the worker retains the "temporarily unavailable" status
   and waits for the earliest expiration or topology/Link generation change, without busy waiting
   or infinite appending of OPENs.
5. Topology generation or Link instance changes clear the old quarantine. After the candidate is
   successful, its own failure count is cleared; after the preferred candidate is ready again, it
   continues to follow the stability window and migration deadline of RFC-0021.

When there is an active circuit, the worker will not use the same active circuit to repeat the OPEN
due to the failure of the preferred OPEN; the old active lease will continue to be maintained by the
renewal/lease mechanism, and migration will not be triggered when the preferred candidate is in
quarantine. This way runtime failures only block the current migration and do not turn available
data paths into black holes.

When the active circuit's renewal send encounters local control plane admission backpressure or a
cancelable control-stream send timeout, the active lease is not revoked immediately; the source and
relay resend within a fixed retry budget. CircuitBroken/lease revocation and OPEN reconstruction are
triggered only when budget is exhausted, ACK times out or Link is closed. This way, transient
controlled congestion on renewals will not be misjudged as end-to-end path failures, while still
retaining independent lease expiration and reconstruction coverage.

### 2. Relay binding failure cleanup

After the relay succeeds at `handle_open` and before and after sending OPEN to the outgoing Link,
the binding, incoming label, outgoing reverse label and lease are regarded as the same resource
group:

- Reverse label installation fails, OPEN forwarding resolution fails, or OPEN send fails: delete
  the entire resource group and try to send the retryable `OpenReject` signed by this node to the
  incoming Link.
- When the downstream `OpenReject` arrives: first find the incoming link and then forward it;
  delete the relay binding after the forwarding is successful or failed to avoid rejecting the
  OPEN and leaving the lease.
- Downstream `OpenAck` forwarding fails: delete the relay binding and try to send retryable
  `OpenReject` to the incoming Link; successfully forwarded ACK does not delete the binding.
- The forwarding of downstream `CircuitRenew`, `CircuitRenewAck` or `CircuitBroken` fails, or the
  downstream has clearly reported that the circuit is invalid: delete the relay binding and try to
  send `CircuitBroken`/feedback signed by this node; the source still uses renewal timeout or
  lease expiry as an independent final guarantee.

All cleanup operations match `(incoming Link instance, CircuitId)` or outgoing Link instance
exactly. They can only delete relay binding and cannot affect the new generation binding of the same
CircuitId on another Link. Repeated and late feedback will be handled as idempotent stale message
when the binding cannot be found.

### 3. authentication, idempotent and boundedness

Candidate fallback does not change wire authentication: each OPEN is still signed by the source,
ACK/Reject still checks for allowed signing public keys, and active leases can still be released
only through `commit_if_current`. Failure feedback generated by the relay can only be passed through
authenticated incoming Link, and the source does not accept unauthorized Link instances.

The quarantine table is bounded by the destination worker lifecycle; backoff counts and expiration
times are not written to the configuration or wire. Relay label/binding clears and reuses the fixed
capacity table and lease deadline, which cannot grow due to duplication of control messages. Failure
feedback sending is only used to speed up convergence and is not the only correctness condition; the
sending end renewal and receiver lease expiry must continue to exist.

## Security and Compatibility impact

No new wire fields and keys are added, and the boundary of the relay only forwarding encrypted
payloads is not changed. When the new source communicates with the old relay, the old relay may not
provide the immediate failure feedback of this RFC, but the source ACK timeout, renewal timeout and
old binding lease still provide final convergence. When the new relay receives the OPEN from the old
source, it will still only process it according to the existing signature, path, ACL and admission
rules.

## Migration and deployment

Upgrade the source and relay daemons first; no migration or additional routing rules need to be
configured. After deployment, you can check the active path, preferred path, and recent migration
errors through status to confirm that the failed preferred path has used a lower priority path
instead of maintaining an empty active path for a long time. Production releases still follow the
existing Nix cache and master release process.

## Testing and Acceptance Criteria

- The unit test verifies that the parser returns all ready candidates. The fallback attempt after
  the first failure can be submitted through identity/generation/authorization verification. The
  failed candidate backs off and the topology changes to resume the attempt.
- Unit test verifies that the relay binding is cleaned up when OPEN forwarding fails or
  ACK/Reject/RENEW feedback fails. Bidirectional label, binding, lease, and duplicate/late
  messages do not delete the new generation binding.
- The privileged three-node test keeps A-B-C preferred multi-hop and A-C direct connection ready
  at the same time, injects B-C control path loss, and verifies that A finally establishes a
  circuit in A-C and port traffic is restored; verify bounded migration after restoring B-C.
- Privileged fault injection covers direct paths, multi-hop relays, downstream restarts, link
  replacement, control plane congestion, duplication and late feedback; the end of the test
  confirms that namespace, TUN, routing, qdisc, firewall rules and daemon processes are all
  cleaned up.
- Pass `cargo fmt --check`, strict clippy, `cargo test --workspace`, and execute the new remote
  script in CI.
