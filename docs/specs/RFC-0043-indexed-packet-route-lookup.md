# RFC-0043: Indexed packet route lookup

- Number: RFC-0043
- Status: Implemented
- Created: 2026-08-23
- Last updated: 2026-08-23

## Background and Problem

`RouteSnapshot` is an immutable routing view of the source packet hot path. Previously, each packet
linearly scanned all `RouteImport` and direct prefix; when the snapshot is built, each route
candidate also linearly searches all secure bindings. Ordinary small configurations have limited
impact, but after SiteSet is expanded into a large number of CIDRs, the search and reconstruction
costs are close to O(prefixes) and O(prefixes × bindings) respectively.

## Goals and Non-goals

Target:

- The snapshot is built using the `(prefix, exit)` index association binding.
- Combine secure candidate and direct priority for the same prefix into one immutable entry.
- Each IPv4/IPv6 packet uses up to 33/129 prefix keys to find the longest matching entry.
- Maintain current longest prefix, health status, priority and direct/secure tie-break semantics.

Non-goals:

- No changes to route configuration format, SiteSet matching, Circuit creation, or health status
  propagation.
- Does not increase flow affinity; health and priority changes still take effect on the next
  packet.
- Does not modify host route installation or platform routing behavior.

## design

The snapshot construction first creates a temporary `(IpNet, exit) -> binding index` map for secure
bindings, then traverses the imports, and merges the candidate index into `HashMap<IpNet,
PrefixRouteChoice>` according to the prefix. direct routes update the maximum direct priority for
the same entry. Duplicate candidate indexes are deduplicated during the build phase to avoid
duplicate additions of hot paths in one configuration.

When searching, the canonical network key is generated from the maximum prefix length of the address
family to 0, and stops at the first existing entry. Only the secure candidates of this prefix are
scanned in the entry, the healthy binding with the highest priority is selected according to the
existing rules, and then compared with the direct priority. If the longest configured prefix
currently has no healthy exit, it will still return Unavailable and will not fall back to a shorter
prefix; this is consistent with the original linear implementation.

`IpNet` key is generated by value on the stack and is not allocated during the search process. The
number of prefixes no longer enters single packet complexity; the number of candidates per prefix is
  still scanned linearly, allowing for atomic reading of real-time health status.

## Security and Compatibility impact

- No changes to ACL, egress authorization, or wire protocol.
- More specific but unhealthy routing will still prevent shorter prefixes from taking over and
  accidentally widening the egress range.
- direct only wins if priority is strictly higher than secure; same priority still takes
  precedence over secure.

## Migration and deployment

No configuration or multi-node migration required.

## Testing and Acceptance Criteria

- Covers longest prefix, health switch, same-priority tie-break, duplicate prefix/candidate and
  direct merging.
- A large number of irrelevant prefixes do not change the selection results.
- Passes fmt, full-featured Clippy, and full unit tests.

## open issues

If a single prefix is   configured with a large number of exits, further grouping can be established
for candidate priority; the current health bit changes in real time by packet, and it is simpler to
retain small vector scans and there is no snapshot synchronization cost.
